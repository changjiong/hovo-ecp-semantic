# 业务交付要求

## 读者与主成果

面向业务负责人、领域专家和需求访谈人员。创建与修订的主成果是 `review.md`，标题为《领域业务知识说明书》，可加具体业务名称。正文、访谈清单和依据索引放在同一份文档内，以业务标题互相链接。审计附件 `coverage.md` 承接逐条台账；`output.json` 保存同一成果的结构化内容，由技能维护。两者不是日常业务阅读入口。

使用客户熟悉的业务语言。必要的专业词首次出现时解释；状态写“材料记载”“分析推断”“建议口径”“待确认”“存在分歧”，不向业务读者暴露内部枚举。编号只辅助引用，不能代替名称、说明和依据。不能把技术字段列表翻译成中文后充当业务说明书。

### 业务阅读顺序

`review.md` 的首要任务是帮助第一次接触该领域的业务读者建立心智模型，而不是展示知识工程过程。创建与修订模式按以下顺序组织业务入口：

1. **业务目标与一句话全貌：** 先说明为什么做、谁使用结果、结果用于什么决定。
2. **核心概念导航：** 先告诉读者这个业务世界里最重要的概念有哪些，以及它们大致解决什么问题；这里不是类模型，不设计继承或平台结构。
3. **业务主线：** 按真实业务主题或过程把主问题串起来，让读者知道事情从哪里开始、经过哪些判断、产生什么结果。
4. **详细知识：** 再进入关键概念边界、逐项业务问题、判断规则、案例和未决事项。
5. **知识工程与审计信息：** 来源覆盖、候选问题归并、编号索引、语义审查统计和版本过程可以保留在正文后部或明确标注为可跳过的追溯区；不能占据业务正文第一阅读屏。

版本与确认状态可以在标题后用一两句简短提示，但不得把版本演进日志、内部修订批次或大段工程状态作为“业务全貌”。业务读者只看前几个章节时，应已经能够回答“这个业务是做什么的、涉及什么、按什么主线判断”。

文档以连贯说明为主，在适合比较规则分支、案例和访谈事项时使用表格。按问题的复杂程度展开，不要求固定篇幅、概念数量或访谈轮次。简短不等于省略关键定义和判断依据；一张术语表或若干规则卡片也不能代替完整业务认识。

## 创建与修订的八项内容

### 一、目标、范围与业务全貌

这一节是业务入口，不是版本日志。说明谁在什么业务过程中需要解决什么问题，结果用于什么决定。写明适用对象、业务时点、制度版本、纳入和排除的范围，以及参与者的责任。资料没有说明时保留未知，不能假定整个行业采用同一流程。

用一段连续叙述串起“事情怎样开始、需要了解什么、由谁判断、结果如何使用”。区分当前做法、制度要求和未来建议。列出本次要回答的业务问题，并链接到具体判断说明。

### 二、处理范围与残余缺口

正文只提供来源级概览、本轮深度审查的业务主题、尚未审查及重要缺口的影响，并链接 `coverage.md`。材料读取、材料映射、业务含义审查各自报告；不能用“全部已覆盖”掩盖尚未拆解的业务含义。全量条款、原文摘录、字段及对象引用清单放在审计附件，正文不嵌入逐条覆盖表。

### 三、关键概念与已有认识

关键概念至少讲清业务定义、适用边界、同义称呼、容易混淆但不同的概念、一个实例和一个反例，指出相应来源与确认状态。不存在可确认定义时，列出候选含义与分歧，不编造标准答案。

例如“已登记的持有人”“实际持有权益的人”“经核实认定的受益所有人”代表不同认识，不能因姓名相同而合并。这里只澄清业务含义，不设计类继承、技术属性或图拓扑。业务固有属性仍要解释，例如比例的分母、时间的业务含义；源字段名称留在来源索引中。

重要业务陈述要能定位到原文。分别说明“材料写了什么”“当前采用或尚未采用什么”“整理者据此推断什么”，防止把转述当成已核实事实。

### 四、业务问题与判断依据

每个业务问题形成一段可复核的解释，至少回答以下事项；简单查询或概念问题按实际需要缩短，不强造决策树：

1. **要解决什么、谁使用结果：** 明确问题和使用边界。
2. **需要知道哪些事实：** 对象、状态、时点、度量口径及必要证据；不能只列数据字段。
3. **依据为什么适用：** 原文位置、适用范围、版本、前提和采信限制。材料冲突时列出双方依据及尚未裁定的影响。
4. **怎样判断：** 依业务顺序说明分流条件、计算或比较、中间判断、例外及优先级。每一步说明为什么可以进入下一步；优先级未知时明确停止相应分支。
5. **能得出什么、不能得出什么：** 区分事实报告、计算结果、判断建议和经授权认定。相关性不能当成因果，未找到证据不能当成不存在。
6. **缺证或矛盾时怎么办：** 哪个结论暂不能作出、需要补什么、由什么角色核实，不能自行把未知补成“否”或默认兜底。

规则即使单列目录，也必须回到问题中解释其作用。禁止用“调用规则引擎”“计算置信度”“满足条件即通过”代替判断机理。这里交付的是有证据支撑、业务人员可以复核的推理说明，不索取或记录模型的私有内部思考。

### 五、案例与结果边界

按业务问题选择能检验不同结论的正例、反例、边界、缺证案例；确实不适用时写原因，缺材料时明确缺口。每个案例包含具体业务背景、已知事实及时间、所用依据、关键判断步骤、预期结果、不得作出的结论、待确认之处。正文精选有区分力的案例；全量案例登记在审计附件。不能用“事实完整且满足条件”代替输入事实，也不能为了四个标签重复同一案例。

预期结果来自适用依据或真实确认，不能从本次生成的规则反过来证明规则正确。合成案例须明确标记；可以用来讨论口径，不能证明客户事实或实际制度已成立。边界值的两侧和边界本身按问题需要说明。反例必须能揭示某个错误判断，而不只是把正例的结论换成“否”。

### 六、分歧与需求访谈清单

每项问题必须能够直接问给业务人员：提供触发问题的材料及原文位置、尚不明确的业务含义、已有不同说法或候选处理、建议及依据（不足时明确暂不推荐）、对结果和后续落地的影响、关联案例、适合回答的责任角色。

同时记录未解决前可以做什么、不能确认什么，以及需要补充的证据。答复区写“待访谈”直到取得真实答复，不预填姓名、日期、同意或默认选项。不能只写“请确认规则是否正确”。访谈后将答复回写到具体概念、规则和案例，说明哪些内容变化、哪些需要重新确认。

### 七、来源与依据索引

用业务可识别的材料标题列出提供方、版本、日期、原文位置、支持的具体认识和使用限制。正文链接直接指向对应条款或本索引条目，不能让读者先去 JSON 查 ID 再找原文。资料未取得、无法定位或适用性未核实时，明确保留缺口。保存来源不等于认可全部内容。

### 八、待确认范围与审阅记录

列出说明书版本、本次待确认的业务问题、已确认范围、尚未确认内容及影响。默认交付可审查草案，不能因没有专家回复就伪造确认或只交空表。

分别记录四项目标的作者自查结论及正文位置、业务读者的实际复述或疑问、领域责任人的真实确认。来源回读自查也要写明涉及哪些条款和问题，不能因抽样通过而推广至未审范围。没有执行的审阅写“尚未开展”，有缺口写具体未决事项。正式确认记录由技能关联到固定文件版本与摘要，业务读者只需按业务事项答复。

## 审查模式

只审查既有文件时，交付《领域业务知识审查意见》，仍使用 `review.md`。内容为审查范围、总体判断、逐项发现及原文位置、业务影响、修订建议、访谈事项和审查限制；不要求重建完整说明书。没有发现时写核对范围和依据，不能生成占位问题。四项目标在本次可见材料范围内逐项评价。

## 文档与附件的一致性

`output.json` 是同一知识版本的结构化记录；业务正文和审计附件均从它投影。业务结论不能只藏在审计附件，正文新增的事实、前提、时间、例外、案例预期与禁止结果也必须回写结构化内容。两份文档与 JSON 的实质差异会阻止完整交付声明。

为使定位可检查，在对应的可读内容前放置 HTML 锚点 `<a id="K.Q1"></a>`，使用已有对象 ID；链接文字用业务名称。业务对象 ID 不得使用 `section-` 前缀，不能只补空锚点。

| 文件 | 内容与定位职责 |
| --- | --- |
| `review.md` | 业务全貌、概念、问题判断、精选案例、访谈、来源和确认；定位全部问题、概念、规则、未决事项、来源。七个固定章节锚点：`section-scope`、`section-concepts`、`section-judgements`、`section-cases`、`section-interviews`、`section-sources`、`section-confirmation`。来源概览使用 `section-provisions`，只展示来源级摘要及缺口，可并入范围或来源部分。必须有到审计附件的可读链接。 |
| `coverage.md` | 全量条款覆盖、陈述、案例、候选问题及归并理由、流程补查；定位全部 ProvisionCoverage、Statement、Case、候选及补查记录。章节使用 `section-provisions`、`section-statements`、`section-cases`、`section-discovery`；注明对应业务文档和版本。 |
| `output.json` | 保存来源引用、业务对象、覆盖及发现记录、确认状态，并在 `files` 登记唯一业务文档和审计附件的真实路径、相同内容版本和摘要。Markdown 的 `contract_version` 为 `text/markdown`，JSON 合同为 4.0.0。 |

只审查既有文件时只需 `review.md`，使用 `section-scope`、`section-findings`、`section-interviews`、`section-limitations` 并定位全部发现，不强行生成新的覆盖台账。

脚本只检查文件、版本、摘要和定位；含义是否完整、问题是否合理、正文是否好读，仍按 [审阅方法](review-guide.md) 检查。分离文档不能减少来源清单和逐单元覆盖要求。

完整业务阅读示例见 [设备维护知识说明书](../examples/equipment-maintenance.md)。示例展示成品深度，不是客户制度或已完成的人类验收。
