# 交互式评审

业务知识说明书完成后应先让业务人员以会话方式审阅，而不是默认将确认留到一个不确定的后续环节。

## IN_SESSION

先展示范围、关键概念、判断依据、案例、冲突和待确认事项；然后按业务标题提出可以直接回答的问题。先提供一个具体案例和当前判断，再说明尚未解决的含义或选择及影响；业务人员按问题标题作答，无需核对数千个条款编号。每项答复记录答复者、角色、时间、范围、原话或忠实摘要，以及对概念、规则、案例和后续模型的影响。只有真实答复覆盖的事项可以形成确认记录；未覆盖事项保持待确认。

## DEFERRED

用户明确选择跳过本轮评审时，交付待审草案。当前无人能够作答也可先交付草案，但应记录评审尚未开展，不伪造用户选择了后审。说明书列出未审范围、恢复时要回答的问题、所需材料和影响。`DEFERRED` 是正常的后审路径，不是失败，也不等于批准；后续使用草案时必须保留其待审状态。

## 共同边界

作者自查、工具检查、智能体建议和没有答复的用户消息都不是业务确认。实质修改后重新固定版本，旧答复不自动覆盖新版本。

## 延续已有答复

先检查本轮及前序会话的真实答复。用户已经明确的业务口径按原意使用，保留“用户口径”和制度原文的区别，不因缺少正式签署信息而重复询问相同业务选择。尚未获得精确文件版本的批准，只影响正式确认状态；不能把已答事项重新标成业务含义未知。

仅询问新增例外、仍含糊的范围、相互冲突的口径或实质修改所影响的内容。若只是等待读者评审样章，把该事项独立登记为待答复，继续其他已授权任务。用户沉默、时间经过、任务脚本结束都不会自动解除未决事项或等于批准。
