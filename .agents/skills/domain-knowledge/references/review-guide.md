# 业务审阅与访谈方法

主交付物及内容要求见 [业务交付要求](business-delivery.md)，完整成品样式见 [设备维护示例](../examples/equipment-maintenance.md)。示例使用合成资料，不是客户规则或实际验收证据。

## 作者先做内容核对

按业务问题逐项阅读说明书，并回到来源核对重要认识。自查必须记录具体段落和未解决问题，不能只填写“通过”。

| 目标 | 实际核对动作 | 需要退回修订的情况 |
| --- | --- | --- |
| 概念正确 | 用原文、实例和反例核对定义及相邻概念；区分角色、材料记载与现实事实 | 循环定义、同名即同义、用来源字段定义概念、把缺证当作否定 |
| 业务可理解 | 仅阅读业务说明书，核对能否连贯说明参与者、业务过程、术语和结果用途 | 必须打开 JSON 才能读懂；只有目录或术语清单；用技术词替代业务解释 |
| 认知机理可审查 | 对每个问题沿事实、依据、判断步骤、例外和结论走一遍，再改变一个具体事实、时间或证据检查边界 | 有结果无过程；前提未满足仍跳到结论；冲突优先级、阈值或兜底未经依据自定 |
| 能用于访谈确认 | 按清单模拟提出问题，核对对方需要作何选择、影响什么、如何记录答复 | 只有“请确认”、没有依据和影响；替对方填写同意或虚构责任人 |

先按 [问题发现与归并](question-discovery.md) 从原文独立列出义务、条件、例外、证据和时间，再对照候选清单及问题目录。审查者不能只沿作者现有的目录找证据，否则目录外的遗漏会被再次忽略。审查已有多少问题不构成配额。

再双向对照业务正文、审计附件与结构化记录：重要内容不能只藏在 JSON 中，正文新增的业务断言也不能没有依据、状态和对应登记。阈值、单位、时间、例外、案例预期与禁止结果尤其需要逐项一致。

## 业务读者复述验证

业务人员愿意参与审阅时，先交说明书和业务问题，不要求阅读附件；选择当前范围的重要问题，邀请对方用自己的话说明：

1. 这个概念指什么，什么情况不属于它？
2. 已知这些事实，为什么会得出这个结果，什么变化会改变结果？
3. 哪条依据适用，哪里还有分歧或证据不足？
4. 当前需要谁确认哪件事，答复会影响哪些案例或后续要求？

记录实际读者角色、审阅日期、文件版本、问题、真实复述或疑问、对应修订。不能用生成的标准答案冒充读者答复；作者自查和另一个智能体审阅都不等于业务人员已理解。

如果读者需要借助技术附件才能回答，先修订业务说明；如果无法判断来源或规则是否适用，保留领域确认事项。没有读者参与时，报告“作者已自查，业务可读性待实际读者验证”，不得自动记为已验收。

## 领域确认与内容冻结

领域责任人对具体概念、规则、例外和案例逐项确认，并保留实际答复、范围、时间及固定版本。阅读顺畅不代表业务含义正确；认可一条定义不等于批准整份说明书。重要分歧只影响依赖它的结论，其他已具备依据的内容仍可交付。

获得新答复后先列出发生变化的业务含义，再更新说明书及附件，并标记受影响的案例和下游需求。推断后来获确认，仍保留其推断来源与当时前提，不能改写成原文直接记载。

## 证据措辞

- “文件与覆盖检查完成”：只指实际执行的结构检查。
- “作者内容自查完成”：有逐项自查记录，不能替代外部审阅。
- “业务读者已验证可理解”：须有该读者的实际复述或疑问及相应处理记录。
- “业务内容已确认”：须有责任人对精确版本和具体范围的真实确认。

未完成事项保留真实状态，不合并成一个总“通过”。

## 判断问题抽象是否合适

从实际要做的业务决定核对问题边界：两个问题若使用者、输入和处置结果不同，应分别回答；同一决定下依赖顺序清楚的分支可作为子问题。跨流程同名概念也不能在含义不同的情况下合并。每次合并记录保留了什么、去往哪个问题；排除要有范围理由。

用四种反向追问检查：这条制度要求在哪回答？这个答案覆盖了哪些前提与例外？某个参与者在该阶段是否仍无从行动？改变一个关键事实后，答案是否指出相应的新分支？不能为追求短目录而隐去独立决定，也不能把每个报文字段都包装成业务问题。

先选择不同类型的几个主题做完整样章，请业务读者实际试读；记录不理解的措辞、漏掉的动作和错误分流，再推广。样章反馈是局部证据，未推广的范围保持未审。
