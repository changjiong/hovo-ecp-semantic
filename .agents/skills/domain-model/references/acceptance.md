# 验收清单

- [ ] 精确输入引用、摘要、知识依据和模式通过；FULL_BASELINE范围等于知识全部问题。
- [ ] 业务审阅稿先给出领域模型总览：现有模型元素按现实对象、角色、关系与业务事实、证据、业务过程、判断/结果、任务等业务层次分组，并展示关键对象引用关系和主要过程；读者无需先逐条阅读字段才能知道模型骨架。
- [ ] 每个对象名称有来源、具体业务句子、正反例和独立理由；身份解释能够区分现实实例。
- [ ] 人/组织/对象、关系、判断、证据、时间连通；角色承担者、Ref目标和基数明确。
- [ ] 本次范围内全部已确认 Term（业务概念）/Rule（业务规则）均被承接、合并或显式排除；全部上游 OPEN（未决）均有去向。规则七要素逐项对应，例外与缺证行为未遗漏。
- [ ] DSL2 作为规范化领域模型 IR（中间表示）使用：语法、输入输出绑定、结果类型、依赖、流程读写、状态守卫和时间含义通过检查；本地求值只作为有限验证辅助，不以“可执行全部业务”作为完成门槛，也不因复杂算法暂未实现而把明确业务语义降级成人工判断。
- [ ] 固有人工判断具有完整准则与责任；未决口径和语言能力缺口分别记录，不互相替代。
- [ ] Question（业务问题）用于二次覆盖检查，没有暴露整块未建模的业务决定；Case（案例）沿用上游 input_facts / expected / forbidden（输入事实/预期/禁止结果），模型只解释所用模型元素，不改写案例真值。
- [ ] 案例逐步解释与实际执行状态分开；执行声明能追溯具体输入、结果、模型摘要和证据。
- [ ] review.md采用业务语言，coverage.md保留完整技术矩阵，均从相同DSL确定生成且字节一致。
- [ ] 修订前旧版模型、请求、审阅稿、覆盖表、交接和原反馈已归档；当前目录只有一个清晰入口。
- [ ] 结构、求值、语义审查、业务评审、正式确认分别记录；不凭PASS制造确认。
- [ ] 语义评估覆盖本轮高风险失败：抽象难懂名称、对象平铺导致看不出模型骨架、遗漏对象端点、通用 id（标识）身份、只做问题覆盖未逐条承接规则、人工裁定与未决口径混淆、为本地执行而膨胀通用 DSL（领域模型专用语言）。
- [ ] 另一无关领域也验证机制适用性；仅语法示例不能宣称泛化质量已证实。
- [ ] 技能、规范、Schema、脚本、样例、接口和报告版本一致。下游未支持DSL2时不声称平台交接完成。
