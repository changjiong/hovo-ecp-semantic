# 模式、替代方案与反例

领域模型选择取决于业务对象、业务关系和业务判断，不以物理数据结构、类数量或执行便利性决定形状。

| 情形 | 推荐决定 | 必查反例 |
| --- | --- | --- |
| 两个现实对象之间有稳定联系 | 建 business_relation（业务关系） | 是否为了省对象把关系塞成某个对象的 Ref 字段 |
| 关系有比例、权利类型、期间或证据 | 把这些作为关系自身属性/语义 | 是否把关系属性错误放到任一参与对象 |
| 两类对象身份、生命周期或适用规则不同 | 保持两个业务对象 | 是否用 kind 字段合并后产生非法组合 |
| 角色依赖承担者、对象和期间 | 建业务角色关系 | 角色名称是否被误当成承担者永久本质 |
| 来源文件支持一个事实 | 文件作为证据，事实/关系单独表达 | 增加第二份证据是否误增第二个业务事实 |
| 计算需要路径/步骤/节点 | 优先作为实现或计算视图 | 业务人员是否真的管理“路径步骤”这个业务对象 |
| 阈值、布尔、日期判断 | 写 business_decision 的业务准则 | 是否为了本地求值引入表达式树 |
| 机构岗位负责人工判断 | 写 human_boundary | 是否把机构治理岗位扩张成目标领域业务角色 |
| 邻接领域结果被当前判断使用 | 建 external_context | 是否复制邻接领域对象、流程和规则 |
| 上游 OPEN 只影响外围流程 | 只做 issue binding | 是否错误升级为 MODEL_GAP |
| 上游 OPEN 阻止核心关系/判断定义 | 建 MODEL_GAP | 是否把未知事实直接补成默认值 |
| 简化/特殊识别路径 | 判断必须写明最终人选/角色语义 | 是否只输出“可简化”标签，仍让下游猜人选 |

名称或标识不同本身不能证明现实对象不同；缺少事实也不能证明事实不成立。后续采用何种算法、平台或数据结构，不改变本阶段业务模型。
