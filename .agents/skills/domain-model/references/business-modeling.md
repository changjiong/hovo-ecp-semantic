
# 业务领域模型建模方法

## 第一原则：模型属于业务，不属于实现

Domain Knowledge（领域知识）讲清“业务知道什么、怎么判断”。

Domain Model（领域模型）只把这些知识背后的业务世界结构化：业务对象 → 业务关系/业务事实 → 业务判断 → 业务结果。

不要为了后续代码方便而扭曲业务结构。

## 对象不是“最少类数”

最少模型不是最少 Type（类型）。

真正的最小模型是：没有多余技术结构，同时没有丢失业务区分。

如果合并两个概念会出现身份条件不同、生命周期不同、可参与关系不同、适用规则不同、必填属性不同、大量 kind 分支或业务上不可能组合，就必须拆开。

例如自然人和组织都有名字，但不能因此合并成一个 Party（当事人），如果“候选自然人”关系因此可以指向组织。

## 关系优先于技术路径

股权穿透的业务事实首先是：
    甲 --持有20%--> B
    B  --持有60%--> A

“路径”“路径步骤”“图遍历”通常是计算视图，不是核心业务对象。

只有业务本身确实管理“某条路径”作为独立可审计对象时，才把路径建成业务对象。

## 业务角色和机构责任分开

客户世界的角色，例如法定代表人、日常管理人、分支高管、信托委托人/受托人/受益人、产品管理人，属于目标领域。

机构内部尽调人员、风险岗、合规岗、审批人通常属于机构治理外部上下文。

人工判断的责任边界写在 business_decision.human_boundary，不因此创建一套机构岗位领域模型。

## 业务判断不是执行规则

业务判断保留输入事实、判断准则、结果、UNKNOWN、非充分事实、证据和人工边界。

不需要在 Domain Model 中提前决定算法、数据库查询、表达式语言、工作流或部署方式。

这些属于 ECP 语义编制或运行实现。

## 特殊路径必须有“人选语义”

简化/特殊路径不能只表达“可以简化”。

必须表达：什么条件 → 允许什么识别路径 → 应识别/认定哪类自然人。

否则模型没有完成业务交接。

## 证据是业务的一部分，但证据不是事实

代持协议.pdf 是证据。

“甲名义持有、乙享有最终权益”才是业务关系。

证据对象可以独立存在，但不能用“有一个文件”代替“业务事实已经成立”。

## 外部上下文只留接口

本领域只声明“我需要外部领域给我什么事实”，不要把邻接领域搬进来。

例如 UBO 需要 AML/KYC 风险结果时，只声明风险输入，不建立完整 AML 风险模型。

## OPEN 不是 MODEL_GAP 的同义词

只有 OPEN 导致核心对象、关系、判断无法确定，才是 MODEL_GAP。

如果 OPEN 仅影响报告时限、系统查询、内部审批、外部数据来源或邻接风险治理，则保持为外部未决，不污染核心模型完成度。

## 好模型的判断标准

业务人员应能回答：
- 我们业务里有哪些东西？
- 它们之间是什么关系？
- 哪些事实会改变判断？
- 怎么得到业务结果？
- 什么情况下不能下结论？

如果必须先理解 DSL、表达式、流程图或技术 ID 才能回答，上述模型就还不是业务领域模型。
