# 模型审查示例

采用设备维护的合成教学场景，不表示已取得知识确认或执行了正式建模任务。真实创建和修订仍遵守知识确认入口。

## 从知识到结构

| 要素 | 业务定义 | 必查反例 |
| --- | --- | --- |
| 设备 | 被持续管理的实际设备 | 改名不应创建新设备 |
| 保养事实 | 对指定设备完成一次保养的业务事实 | 两份证明不能算两次保养 |
| 在用状态 | 指定时间范围内设备的使用状态 | 没有状态记录不等于停用 |
| 维护安排 | 依据规则提出的维护工作 | 提出安排不等于已经执行 |

上次保养日期、保养周期及其单位是业务属性；源系统字段名不进入这张定义表。

## 政策与判断

时间政策绑定保养事实及其日期属性，分别说明业务发生时间和获知时间，以及日期未知时的行为。证据政策绑定保养事实，说明完成证明如何采用、重复证明如何去重、相互冲突时怎样处理。

判断步骤依次说明：选择符合范围的设备及保养事实；根据已确认起算口径计算业务量；应用在用范围与到期规则；产生维护安排或待核实结果。每一步引用已定义对象、属性和业务规则，声明缺数据时的行为；这不是某个平台的可执行脚本。

## 评审问题

- 设备换名、重复证据、状态变更时，哪些身份不变？
- 周期单位和起算时点是否一致，边界当天怎样判断？
- 证据缺失或冲突时，能否仍产生正式安排？
- 每个知识案例能否用这些对象解释，是否保持原预期与禁止结果？

结构检查只能帮助发现遗漏和矛盾引用；这些业务问题须结合知识依据与责任人的判断审查。
