# 领域模型

核心交付是完整的 `model.yaml` 及其同源业务审阅稿。领域模型回答：

> 已确认的业务知识背后，稳定的业务结构是什么？哪些事实、关系和判断连接起来，才能无歧义表达这些知识？

`model.yaml` 是平台无关的 Domain Model IR（领域模型中间表示），用于业务语义交接和机器检查，不是数据库模型、ECP 平台资产、规则引擎或另一套生产运行时。

## 产物目录

调用方项目的 `domain-model/`（或同等阶段目录）根部只放 `input.json`、`model.yaml`、`output.json`、`review.md` 和 `coverage.md` 等正式交付。生成请求、任务记录、校验结果和调试过程放在该阶段的 `process/`，旧模型和旧证据放在 `archive/`；不得把运行产物写入技能包目录。

## 输入边界

先读 [合同](contracts/README.md)、[业务建模方法](references/business-modeling.md) 与 [Domain DSL（领域模型专用语言）](references/domain-dsl.md)。

本技能只消费固定版本的领域知识基线：

- Term（业务概念）；
- Rule（业务规则）；
- Question（业务问题）覆盖框架；
- Open Issue（未决事项）；
- Case（案例）基准及其 expected / forbidden（预期/禁止结果）；
- 来源和确认引用。

**不重新读取原始法规、PDF（便携式文档格式）、MinerU（文档解析工具）输出、数据库表字段、DDL（数据定义语言）、SQL（结构化查询语言）或 ECP（可执行语义协议）算子来改写业务含义。** 如果领域知识缺失或存在冲突，退回 `domain-knowledge（领域知识形成）`；不能在建模阶段自行补一套新业务规则。

PRODUCE（创建）/REVISE（修订）固定 knowledge_ref（知识引用）、scope_mode（范围模式）和 knowledge_basis（知识依据）。DRAFT（草案）允许承接未确认知识但必须保留 OPEN（未决）；CONFIRMED（已确认）入口必须有真实 ConfirmationRecord（确认记录）。

## 模型完整性的主轴

模型完整性以**范围内领域知识是否被承接**为主，不以问题数量或模型元素数量为主：

1. 每个范围内已确认 Term（业务概念）必须被模型沿用、合并或明确说明无需成为独立模型对象；
2. 每个范围内已确认 Rule（业务规则）必须被模型表达，或明确标为本模型范围外并说明理由；
3. 每个上游 OPEN（未决）必须继续可见，不能通过建模默认值关闭；
4. Question（业务问题）用于检查是否存在整块业务决定没有模型支撑，但不是模型最小交接单元；
5. Case（案例）沿用上游事实和预期作为验证基准，模型只解释“哪些模型元素支持这个案例”，不得重写案例真值。

FULL_BASELINE（全量基线）表示承接固定知识版本中本次业务范围的全部已确认知识，并对全部 OPEN 给出去向；EXPLICIT_SUBSET（显式子集）只能来自用户明确限定的业务范围。

## 处理步骤

1. **固定知识基线。** 登记范围内 Term、Rule、Question、Case 引用及 OPEN 事项。先按知识确认状态确定哪些内容可建模，不能先从字段或 DSL 便利性反推业务范围。
2. **抽象稳定业务结构。** 用具体业务句子识别 Entity（实体）、Role（角色）、Fact（事实）、Relation（关系）、Event（事件）、Decision（判断/结果）和 Task（任务）。对象只有在具有独立业务身份、参与者或生命周期时才独立存在。
3. **连接对象与时间。** 每条关系明确两端、方向、基数、有效时间和业务依据。时间属于现实业务关系/事实，不是为了技术实现才增加的字段；UNKNOWN（未知）不能自动变成 false（否）或 0。
4. **逐条承接领域规则。** 对每条已确认 Rule 保留 scope、preconditions、conditions、result、exceptions、missing_evidence、effective_period 七要素。规则输入绑定真实业务事实，输出绑定业务判断或派生事实；前序判断只有在业务上确实形成新事实时才成为后续输入。
5. **区分自动规则、人工裁定和未决知识。** 可确定计算写清数学/业务语义；固有人工判断用 Judgment（人工裁定）表达其证据、准则、责任和输出；制度/机构口径未确定则保持 OPEN。语言暂时不能执行一个已明确业务逻辑，不等于该业务逻辑是人工裁量。
6. **只形式化必要计算。** 简单阈值、布尔组合、比例乘加、日期比较等稳定业务语义可用 DSL 表达并做有限本地校验。复杂图遍历、循环股权处理、数据库查询、生产状态机和平台执行算法若不是领域模型本身的稳定业务概念，不继续扩充 DSL；只需要写清输入、输出、业务语义、未知处理和适用前提，交由后续实现阶段选择算法。
7. **用上游案例验证。** 不创建第二份案例真值。引用固定 Case ID，逐步说明所用模型对象、事实和判断；模型解释与实际执行状态分开。真实运行或 ECP 编译属于后续阶段。
8. **生成业务视图与审计视图。** `review.md` 先展示领域模型骨架、关键对象关系和主要业务过程；`coverage.md` 保存 Knowledge → Model 映射、规则七要素和问题覆盖；`output.json` 只做交接索引。文档都从同一 `model.yaml` 确定生成。
9. **专家审阅抽象是否改义。** 业务专家不需要审核 YAML（层级配置格式）语法，而应确认：对象边界、关系方向、业务状态、人工裁定、规则输入/输出和时间含义有没有改变已确认知识。

## Domain DSL（领域模型专用语言）的边界

DSL 的首要目标是**无歧义表达和静态检查业务语义**。表达式和本地 evaluate（求值）只是有限验证辅助。

允许保留已经存在的通用表达能力，但新增能力必须先通过一个判断：

> 如果去掉本地求值，这个构造是否仍是跨实现、长期稳定的业务语义？

如果不是，就不进入 Domain DSL。不要为了让 `model.yaml` 自己跑通而加入数据库访问、网络调用、平台算子、领域专用图算法或生产工作流执行器。

复杂计算不能因为当前 DSL 不方便实现，就被降级成“人工判断”；同样也不能为了自动求值而把实现算法伪装成领域概念。

## 交付与完成边界

交付：

- `model.yaml`：唯一规范化领域模型；
- `review.md`：业务模型审阅视图；
- `coverage.md`：知识到模型的映射与缺口；
- `output.json`：交接索引；
- 实际验证记录（如有）独立保存。

一个模型范围可以完成，即使存在明确 OPEN，但至少满足：

1. 范围内已确认 Term / Rule 均已被承接或显式排除；
2. 上游 OPEN 未被静默关闭；
3. 对象、关系、事实、判断和时间可以连成业务解释链；
4. 固有人工裁定与未决业务口径明确分开；
5. Question 覆盖没有暴露出整块未建模的业务决定；
6. 相关固定案例可以由模型解释，且没有改写上游 input_facts / expected / forbidden；
7. 完成不依赖本地执行全部业务，也不以字段/对象/规则数量证明质量；
8. 下游在不重新阅读原始制度的前提下，能够根据该模型继续做 ECP 语义转译。

当前模型目录保持唯一入口；历史字节归档，不建立并列“完整版/最新示例”。完成本技能后结束，不自动启动 ECP 编制。
