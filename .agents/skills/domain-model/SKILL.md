# 领域模型

核心交付是完整的 `model.yaml` 及其同源业务审阅稿。先完成业务建模，再用 DSL 表达；YAML 合法、对象数量多、引用齐全都不能证明业务建模完整。

## 入口

先读[合同](contracts/README.md)、[业务建模方法](references/business-modeling.md)与[DSL](references/domain-dsl.md)。具体方法按[索引](references/handbook-index.md)加载。知识输入合同4.0.0随包离线保存；不从原始制度重新抽取业务口径。

- PRODUCE：固定知识 ArtifactRef、scope_mode、问题范围、knowledge_basis 和 review_mode。默认 FULL_BASELINE，必须覆盖知识的全部问题；只有用户明确限定范围才用 EXPLICIT_SUBSET。
- REVISE：另固定旧版 subjects 和 change_request。先完整归档旧版，再修改当前目录；新内容版本不继承旧确认。
- REVIEW：只审查指定既有模型，交付意见，不擅自改写。
- DRAFT：可采用未确认知识，逐项承接全部上游 OPEN；模型保持待审。
- CONFIRMED：须有外部 ConfirmationRecord，绑定精确知识字节及本次范围；不等于模型已确认。
- IN_SESSION 支持逐项对话；DEFERRED 支持线下转交与反馈回流。方式与知识依据独立，不因技能结束自动结束评审。

## 处理步骤

1. 固定范围与完成条件。登记全部问题、规则、案例和开放事项；不能先选容易演示的几个问题，再按选中范围宣称全量完成。
2. 用业务句子和真实含义解释每个候选概念。定义名称来源、具体正反例、身份依据和独立存在的理由。区分实体、角色、关系、属性、结果与计算中间量；同形且同生命周期的信息可合并，业务不同不能为了少几个类型而强行合并。
3. 连接对象。关系明确两端、方向、数量、适用对象和时间；业务身份不能只解释为通用 id。字段声明类型、单位、取值和未知处理。
4. 逐条解构规则：范围、前提、条件、结果、例外、缺证处理、时间要求。每项映射实际字段、表达式、约束、迁移或人工判断；条件只关联类型名称不算完成。规则输入/输出绑定字段，前序规则输出显式成为后续输入。
5. 表达时间和过程。区分实际生效、终止、获知、请求和反馈时点；保留真实中断。流程声明读取、写入、所用判断与依赖顺序；声明流程不代表已执行它。
6. 区分人工裁定与缺口。固有人工判断应完整定义准则、证据、责任、输出及复核，可算建模完成；未决业务口径保留 OPEN。已知可计算逻辑若语言不支持，登记语言能力缺口并补实现，不能改称人工判断来过关。
7. 用 DSL2 和合同5做结构、绑定、依赖及逐条覆盖检查；另做语义审查。案例保留原始输入、expected、forbidden，逐步说明模型如何得出结果。实际执行记录与解释状态分开。
8. 从同一 DSL 生成 review.md、coverage.md、output.json。业务稿使用业务名称、问题和案例；内部标识与全部规则要素表放 coverage.md。不单独改生成文档。
9. 按[交互评审](references/interactive-review.md)处理反馈，按[验收](references/acceptance.md)检查完整性、案例行为和待确认事项。重新生成受影响成果，保留版本及证据。

## 交付与边界

交付 model.yaml、review.md、coverage.md、output.json、实际验证报告及原始评审记录。当前模型目录保持唯一入口；历史字节归档，不能建立并列的“完整版”和“最新示例”让读者猜。

DSL2是受限声明式语言，运算符由规范封闭定义；没有任意脚本、数据库访问、ECP运行或真实业务写入。跨规则依赖和流程只作静态契约检查，单规则/单迁移可本地求值。未实现的图算法必须显式标明；循环股权等领域专门口径放领域成果，不固化为本通用技能规则。

结构 PASS、案例求值、语义审查、责任人确认分别报告。当前0.7.0为开发候选，最终证据以reports及具体交付记录为准。消费者必须显式支持DSL2/合同5后才能正式交接；本技能不证明平台可编译。
