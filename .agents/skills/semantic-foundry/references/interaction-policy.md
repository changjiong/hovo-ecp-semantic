# 阶段审查、访谈与确认

本次五技能建设方案明确要求阶段确认。一次任务的澄清问题数量不限制必要的确认检查点；不再使用“全流程最多一轮五问”作为推进规则。

每个阶段先完成可以审查的成果，再向责任人展示：本次范围、版本、关键结论、具体案例、仍有争议的事项、建议与替代口径、影响的下游资产。业务人员确认业务含义与案例，不要求他们判断编译器 JSON。

| 状态 | 含义 |
| --- | --- |
| DRAFT | 当前责任技能正在形成成果 |
| AWAITING_CONFIRMATION | 草案与验收资料已准备好，依赖它的下游停止 |
| CONFIRMED | 有真实确认记录，覆盖指定范围与文件摘要 |
| REJECTED | 责任人明确不接受，需要返回当前或上游阶段 |
| STALE | 输入或内容变动，原确认与检查不能用于当前版本 |
| BLOCKED | 缺必要资料、能力、授权或未解决关键冲突 |

知识内容的 SOURCE_STATED/INFERRED/PROPOSED 与工作流确认状态不同。原文明确写出一条规则，不等于客户已确认其适用范围；作者判断合理不等于负责人已签认。

确认记录应保存责任人、角色、实际答复原文定位、时间、事项 ID、采用口径、异议、适用范围以及被确认文件的 ArtifactRef。缺少明确答复时不得填写确认人签字或确认日期。将“继续”作为批准时必须能明确对应刚呈现的唯一版本和范围，否则只作继续当前阶段处理。

默认分别确认知识、模型、平台表达和数据绑定。已有当前版本的有效确认可直接使用，无需反复询问；未来尚未生成的内容不能预先批量确认。某子范围未确认只阻塞它的依赖，其他已经确认且独立的范围可继续。

修改语义或案例预期后重新提交对应负责人；纯封装变更也要刷新字节引用和技术检查，不能沿用旧摘要。确认是独立文件，避免把签认写回已签认的 output.json 后改变其字节。

业务确认、数据只读访问、平台编译、导入替换、发布与运行是不同作用范围。已有操作授权在本任务范围内有效；不得把知识确认当作生产发布许可。编排器负责维持这些记录，不能代替任何责任角色作出批准。
