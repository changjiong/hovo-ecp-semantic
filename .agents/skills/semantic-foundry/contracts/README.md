# 跨阶段合同 1.0.0

五个技能遵循资产身份、版本、摘要、来源和证据约定，分别携带自己版本的输入输出合同。本目录的 [JSON Schema](common.schema.json) 管理编排登记；知识与模型已采用平台无关合同2.0.0，不携带平台生命周期。ECP阶段保留自身合同版本，编制技能通过随包输入合同接收模型2.0.0。合同由 Hovo 维护；公共对象不定义业务模型、ECP wire 或数据库字段。

## 文件和引用

每个阶段输出 `<stage>/output.json` 和供责任人审查的 `<stage>/review.md`。`output.json` 是唯一结构化内容维护位置，审查稿是其业务呈现；其他文件只在确有消费方时产生。所有 `ArtifactRef.path` 相对本次项目根目录，SHA-256 基于实际文件字节。不得包含绝对路径、上级跳转、符号链接、凭据或被全局规则禁止的路径。

`artifact_id` 是稳定身份；`content_version` 随内容变化；`contract_version` 标识结构。依赖使用完整的 ArtifactRef，禁止 `latest` 或只写名称。输入来源、产出文件和证据文件都登记摘要。`output.json` 自身摘要记录在交接它的下游输入或确认记录中，不能把自身哈希写入自身而产生递归摘要。生成文件后计算摘要，再生成引用它的交接文件。

`SourceRef` 指向材料原文与具体页码/段落；`EvidenceRef` 指向实际检查或确认记录，`subject_refs` 固定它证明的文件字节。未知来源日期可明确写 `UNKNOWN`，不得编造日期。业务确认记录按公共 Schema 的 `ConfirmationRecord` 结构记录责任人、角色、真实答复文件、日期、适用事项和每份被批准文件的完整引用；阶段输入的 `*_confirmation.record` 指向该 JSON。确认是独立记录，不能修改已被签认的 output.json 来添加签认；编排登记持有最新确认依据。操作授权按实际用户指令与动作范围另行核对，不伪造为专家签认。

## 进入下一阶段

Schema 合格只是结构条件。接收方还必须核对引用文件存在、摘要相同、版本及合同相符、确认记录覆盖本次输入、范围内关键问题已处理、验收清单有证据。输出 `confirmation=PENDING` 时可以交付草案，明确确认该精确版本的外部记录到达后才可交给下游。作者、脚本或编排器不得自行替业务负责人确认。

知识和模型阶段分别需要领域负责人确认。平台表达需要语义实现负责人确认忠实转译；Mapping 需要数据负责人确认绑定与缺口处理；发布需要目标环境和动作的明确授权。上游的业务确认不授权平台写入。确认只覆盖明确范围；开放问题影响的能力不得被悄悄包括在已确认范围中。

## 独立状态

每阶段只报告自己承担的状态。知识和模型使用结构检查、业务审查及独立确认；ECP交付另行报告编译、发布、运行和业务验收，每个实际执行状态必须引用证据。编排器不能要求前两个技能填造平台状态。尚未执行不能写成 FAIL 或 PASS；下游也不能把上游通过当作自身通过。

## 追溯和变更

使用阶段内稳定 ID 及 `trace` 记录本阶段新产生的边，不复制整条历史。来源到知识、知识到规则、规则到概念、概念到 IRI、IRI 到 Mapping、能力到 Case 均能通过 input_refs 回溯。

下游变更请求使用 `Issue(kind=CHANGE_REQUEST)`，说明现象、证据、受影响 ID、建议、责任人与未处理前行为。确认后由上游技能修订，生成新版本；沿 `DEPENDS_ON` 和输入引用检查受影响资产，旧摘要对应的确认、编译、Run 证据保留为历史，不用于新版本。与变更无关的资产应给出不受影响依据，不能仅凭日期推断失效范围。

## 案例与边界

关键能力至少审查正例、反例、边界和缺证情形。案例是业务验收规格，包含事实、预期和禁止结果，不等于测试代码或实际测试执行。没有事实材料时可用明确标记的合成说明，禁止冒充客户事实。新增或修改测试代码仍遵守任务授权。

五个技能可分别以完整单目录安装，自带所需合同、方法资料和本地工具。公共合同是版本约定，不是运行时共享目录。输入可以由人工、其他工具或其他技能提供，只检查资产与确认，不要求前序技能执行历史。semantic-foundry 仅在需要跨阶段编排时使用；生产技能不读取本包，也不需要 pipeline.json。
