# 金融领域本体语义构建方法论
## V2.0｜审阅修订版

**文档职责：**规定如何将领域认知转化为明确、可共享、可验证的语义模型。

**适用对象：**领域专家、产品负责人、本体工程人员、数据与应用工程人员。

**基线与日期：**以本次对话生成的第一册 V1.0 为基线，落实已确认的审阅意见；2026年9月7日。第二册规定生产与验收，第三册提供受限范围的参考工程。

## 1. 目的、范围与使用方式

### 1.1 本方法论要解决的问题

同一个业务词在不同系统中可能指向不同对象；不同名称也可能指向同一个现实主体。仅共享字段名，不能保证共享业务含义。本体工程的任务是明确领域中采用哪些概念、它们指向什么、如何关联，以及允许由这些陈述推出什么。

本体是对选定领域的显式概念化规范。采用形式语言时，其含义由该语言的语义及具体公理共同限定，并非由名称或图形外观决定。本体可以包含概念知识与实例陈述；本规范在工程交付中将稳定概念模型与来源实例分开管理，以便审阅和复用。[S2]

本方法论遵循三个起点：**建设动因由业务问题决定；建模内容由领域含义及证据决定；完成标准由声明范围内的能力问题和实例验证决定。**本体既不是数据库结构的翻译，也不是对整个金融世界的无边界描述。

### 1.2 描述与执行的边界

本体可以描述任务、控制安排、规则引用、认定结果及动作的业务含义，但不因此承担算法实现、权限执行和外部写回。计算、规则、流程与应用是消费者；消费者对输入类型、计量口径、时点和知识状态的要求，应在首个能力问题切片中反向校验模型，而不是等全领域建完才反馈。

| 制品或能力 | 负责的问题 | 不应冒充的能力 |
|---|---|---|
| 本体、公理 | 对象和关系的含义，以及允许的逻辑推论 | 强制原始记录字段完整、执行审批 |
| 数据约束 | 当前数据在指定阶段是否满足显式要求 | 证明原始材料真实、保证业务结论正确 |
| 确定性计算 | 在声明前提下进行数值和关系计算 | 自动消解法律争议、猜测缺失事实 |
| 业务规则 | 对适用事实进行条件判断 | 代替事实核验或授权确认 |
| 运行与流程 | 组织调用、记录过程、执行已授权操作 | 改写本体含义、制造批准状态 |

### 1.3 规范用语与知识来源

“必须”表示本套手册内部的准入条件；“应”表示需有理由才能不采用的推荐；“可”表示按场景选用。它们不是对所有本体项目的普遍法律或技术强制要求。

文中[S1]为用户提供书籍；[S2]等为标准及原始文献；未标为书中原文的流程、卡片与门禁是本套手册的工程约定。书籍的“7+1”“29句话”用于知识表达与覆盖检查，不被改写成唯一标准或执行顺序。

## 2. 最小充分的建模单元

### 2.1 能力问题先于本体规模

能力问题是模型应支持的可验证问题。它不是一句愿望，而是输入、上下文、执行责任和预期答案的组合。例如，“查询当前股东”必须说明目标企业、业务时点、知识截止时点、事实视图、是否包含法人股东及返回集合的完整性边界。

能力问题可分为：可表达、显式可查询、经推理可查询、经计算可得、经业务规则判定、需人工裁定。后面三类可以支撑建模需求，但不得宣传成本体单独完成的能力。

| 能力问题 | 所需执行责任 | 合理的完成证据 |
|---|---|---|
| 某项权益的持有人是谁 | 事实视图查询 | 查询文件、固定数据及精确集合 |
| 该对象是否继承某上位类型 | 声明配置下的类型推理 | 公理、推理配置及预期推论 |
| 某人间接持股多少 | 路径与数值计算 | 支持条件、输入边、精确数值与路径 |
| 是否构成正式受益所有人 | 适用规则、核实和授权责任 | 规则依据、证据、限制及确认记录 |

### 2.2 最小本体承诺

只建立当前能力问题确实需要、含义可以说明的概念和关系。每个核心元素应能关联到至少一个能力问题，或者关联到该问题所必需的共享定义。

不因资料中出现名词就创建类；不因数据库存在列就创建属性；不因查询可以返回路径就持久化路径对象；不因预期将来复用就导入庞大上层本体。对于已有资产，先核对定义、身份、适用范围、推论后果、维护状态和使用许可，再决定复用、对齐、扩展或不采用。

### 2.3 一个切片的完成定义

一个最小切片必须贯通：业务问题、所需定义、来源实例、可用事实视图、查询或检查、正反例和结果证据。其通过只对已声明的输入范围、规则与执行配置有效。

后续切片只增加新问题必要的语义，同时重跑已有切片。部分输入缺失时，记录依赖阻塞，继续不依赖该输入的工作。对新场景的提速来自复用已经验证的资产，而不是减少真实性要求。

## 3. 概念化：决定业务世界如何被表达

### 3.1 分析视角不等于互斥分类树

实体、关系、关系对象、事件、状态、角色、值、事实断言和证据，是分析候选概念的视角，不能直接生成九个互斥上位类。它们混合了领域存在、表达方式和业务用途。

例如，一份协议扫描件是信息对象，在某次核验中可承担证据作用；协议所记载的法律安排是另一个对象；来源对安排的摘录是断言。上述对象可以关联，但不应因为都被称为“协议”而合成一个资源。

### 3.2 每个候选概念的六项检查

| 检查项 | 必须明确的内容 |
|---|---|
| 定义 | 它是什么、不是哪些相邻概念；给出正例与反例 |
| 粒度 | 一个实例是一项法律权利、持有状态、文档还是来源记录 |
| 身份 | 哪些变化仍属同一对象；什么条件必须产生新对象或新版本 |
| 参与关系 | 起点、终点、方向、上下文、是否需要多元参与者 |
| 时间与计量 | 何时有效；数字的单位、尺度、分母、精度是什么 |
| 消费与验证 | 哪个问题使用它；哪些推论必须出现、哪些不得出现 |

概念评审应围绕这些检查和具体案例，不要求业务专家直接书写形式语言。资料不足时先保留定义待定项，不用模糊的“关联”“涉及”掩盖未解决含义。

### 3.3 何时将关系建成独立对象

简单二元关系可以直接用关系表达。需要比例、权利类别、多元参与者、历史区间、独立引用或版本时，可采用关系对象模式。多元关系建模与对一条陈述附加来源元数据是不同机制；只有来源元数据需求，不自动要求另建法律权益实体。[S7]

本套样板选择“权益持有位置”作为关系对象，因为需要将持有人、发行组织、权利类型、股份类别、分母口径与时间一致关联。该选择不是唯一合法模型；替代模型只要满足同样能力问题及反例，可以经评审采用。

### 3.4 角色、类型与状态

“股东”表示主体相对于特定组织、在特定有效期内的角色，不应被解释为自然人的永久本质类型。这不禁止用具有上下文定义的类描述该角色。法人也可能承担股东角色。

事件表示发生的变化，状态表示特定上下文中的情况。股权转让事件、转让后的持有状态、系统收到转让材料的事件必须区分。没有发生事件数据，不表示状态一定未变化。

### 3.5 不同含义的“必须”

| 类型 | 例子 | 违反或缺失时如何处理 |
|---|---|---|
| 定义性条件 | 公司属于组织 | 检查概念及允许推论 |
| 记录质量要求 | 可计算记录需明确比例 | 保留来源，标记当前不可计算 |
| 算法前提 | 此算法只处理无环比例传递 | 返回不支持，不静默套公式 |
| 合规义务 | 特定认定应完成核实 | 记录未完成义务，不能伪造已核实 |

“业务要求应当成立”不等于“现实世界中不可能出现违反情形”。模型必须能表达未知、缺失和违规，否则会把最需要调查的事实排除在数据之外。

## 4. 身份、时间和计量合同

### 4.1 身份是领域规则，不是字符串相等

应区分来源记录、现实主体、权益对象、来源断言和认定记录各自的身份。无需机械建立五套编号，但不能将一条来源记录的主键直接等同于现实世界身份。

身份合同至少定义标识的发放范围、发放主体、适用时间、名称变化、重复导入、候选匹配、已确认映射与错误合并纠正。名称相同不能作为唯一合并依据；企业更名不应自动新建现实主体。存在可疑同一性时保存候选关联及依据，不直接写成强同一性事实。

IRI（国际化资源标识符）的字面不同，并不在OWL（网络本体语言）中自动证明对象不同。个体同一性、类等价、术语映射也不能互相替代。[S2][S6]

### 4.2 时间必须同时回答两类问题

每个历史任务至少明确业务有效时点与知识截止时点，必要时保留来源观测时间、系统记录时间、采信时间。前两者分别回答“什么时候成立”和“截至何时允许使用已知材料”。

区间端点、日期粒度与时区必须显式约定。本样板使用左闭右开区间；未知终止日与明确持续有效采用不同表示。追溯更正保留原断言，并引用被替代断言。新知识不得反向改写历史任务的输入快照。

“当时所知的历史结果”与“现在回看过去的结果”都可以合法存在，但必须用不同任务上下文区分。时间本体提供表达资源，具体知识截止与采信政策仍属于本项目约定。[S9]

### 4.3 数值必须带计量含义

比例至少说明权利类型、分子、分母、股份类别、数值尺度、有效时点、精度与舍入政策。0.25和25只有在尺度已知且完成转换后才可能等价。

所有权、表决权与收益权不混算。展示舍入值不得用于阈值判断。算法需声明是否支持多路径、循环、特殊股份、代持或不同收益分配；不支持的结构应保留原始信息，并局部阻塞受影响结果。

## 5. 来源断言、证据与可消费事实

### 5.1 四种对象不可合并

来源记录是信息载体中的记录；断言是该来源表达的业务陈述；证据作用是某材料对特定判断的支持或反对关系；事实视图是某任务按明确采信政策选出的可用事实集合。

本体模型不宣布自己掌握绝对真相。对关键判断，应能回到来源、陈述内容、时点、采信依据及限制。PROV-O（来源追踪本体）可用于表达来源关系，但其使用不自动证明材料真实性或来源独立性。[S8]

### 5.2 从断言到事实视图的显式桥接

经典RDF（资源描述框架）的语句重述描述一条陈述，但不会自动蕴涵该陈述本身。保存断言后，必须另行规定如何查询断言或如何组装事实视图，不能以为底层事实自然存在。[S4]

最小链路为：来源记录 → 断言 → 采信记录 → 任务事实视图 → 计算与认定。采信记录至少保留选入与排除对象、依据、责任或政策、记录时间。模型抽取置信度不能替代业务采信。

事实视图必须记录使用的断言标识、业务时点、知识截止时点、采信政策版本、未解决冲突和覆盖声明。同一权益被多个来源重复描述，不得被重复算作多份权益。

### 5.3 冲突判定首先检查可比性

只有对象身份、权利类型、股份类别、分母口径和适用时段相容时，比例不同才构成待处理的值冲突。不同日期或不同权利口径可能同时成立。转载同一上游材料的两个网页不是两份独立证据。

冲突不默认按“最新”“最大”“多数”消解。可以在明确政策或核验依据下采信，也可以保留争议并阻塞相关计算。排除一项断言必须可追踪，不能无痕覆盖。

### 5.4 状态按维度建模

| 维度 | 示例 | 描述的对象 |
|---|---|---|
| 知识与证据 | 已确认、未知、存在冲突、证据不足 | 陈述或判断的知识状况 |
| 业务有效性 | 当前有效、已终止、时间未知 | 权益或安排的现实有效性 |
| 工作状态 | 待补证、待复核、已完成 | 识别或核验任务 |
| 制品验证 | 通过、失败、未执行、不支持 | 某项工程检查 |

上述维度可同时成立，不汇成一个互斥枚举。查询无结果不等于已经证明不存在；缺少数据不自动触发业务兜底认定。

## 6. 形式化语义与校验边界

### 6.1 工具各自承担什么

RDF（资源描述框架）表达资源和关系；OWL（网络本体语言）表达逻辑公理；SKOS（简单知识组织系统）管理术语及概念映射；SHACL（形状约束语言）检查指定数据图上的约束。使用哪些能力由任务决定，不要求全部启用。[S2][S3][S5][S6]

### 6.2 必须掌握的五项区别

| 情形 | 正确解释 | 工程检查 |
|---|---|---|
| 属性声明值域为自然人，公司被填入 | 可能推导该公司也是自然人，而非自动拒收 | 单独验证输入类型；检查不希望出现的类型推论 |
| 公理要求每项权益有持有人，但记录未填 | 开放世界下不必构成矛盾 | 显式字段完整性由数据约束检查 |
| 两个不同名称受唯一性约束影响 | 可能推导同一性，不一定报重复 | 记录标识与实体消歧独立治理 |
| 甲类、乙类互为子类 | 表达实例集合相同，非语言非法 | 检查是否意外等价；分类图无环可另作项目约定 |
| 甲类被约束为空 | 类可能不可满足，但知识库未必不一致 | 区分类可满足性与知识库一致性；应可实例化的核心类为空可判业务质量失败 |

这些区别分别来自类型蕴涵、开放世界、类集合和一致性的标准语义。[S2][S3][S10]不能用“文件通过”概括其全部含义。

### 6.3 形式化前的最小选择

明确采用的语法、语言配置、导入模块和执行工具；写出希望推出及禁止推出的示例。语言配置符合、语法可解析、知识库一致、类可满足、数据符合约束和业务正确性应分项记录。某项未执行或工具不支持时，不得继承其他项的“通过”。[S11]

## 7. 八步构建方法及迭代方式

| 步骤 | 工作内容 | 产物与退出条件 |
|---|---|---|
| 1 范围界定 | 明确业务问题、消费者、纳入与排除范围 | 范围说明；不需要先穷尽整个领域 |
| 2 能力问题 | 定义输入、时点、数据范围、责任与正反预期 | 可执行验收契约，而非仅有问题标题 |
| 3 知识获取 | 读取制度、资料、数据及已有资产，萃取明确陈述 | 来源与定位、术语、争议；用“29句话”检查覆盖 |
| 4 概念化 | 判定概念粒度、身份、关系、角色及反例 | 核心概念卡及必要的建模决策 |
| 5 语义精化 | 完成时间、计量、状态、采信与消费者合同 | 无未披露的关键分歧；未解决项局部阻塞 |
| 6 形式化 | 按选定语言配置表达模型和阶段约束 | 机器文件、推论预期、执行配置 |
| 7 实例与映射 | 将真实或明确合成的输入按身份与口径映射 | 可追踪实例、拒绝及隔离记录、任务事实视图 |
| 8 验证与发布 | 执行正例、反例及变形检查，核对发布完整性 | 分项证据与限制；通过后形成可复用版本 |

八步是依赖关系，不是全领域串行瀑布。每次围绕一个能力问题贯通，再扩展；早期测试发现语义错位，应回到对应定义而不是仅修改期望答案。

书中的“29句话”承担知识描述入口，“7+1”承担覆盖检查。它们允许由资料自动填充、专家补充或标记不适用，不是逐项拷问用户的任务清单。[S1]

## 8. 质量、复用与演进

### 8.1 三种正确性分别验收

领域正确性由知识依据、案例及专业审阅支持；形式正确性由相应工具证明；使用正确性由映射、查询、计算和消费者合同测试证明。三者任何一项通过，都不能替代其他项。

### 8.2 复用以含义一致为前提

优先检查既有资产，而不是先发明公共层。相同术语不保证相同概念；近似映射不使用强等价。只有定义、范围、身份与推论可以共享时才复用。共同概念可抽成模块，场景专用规则与系统表名不进入公共定义。

无需让所有场景建满固定四层。模块化的理由应是独立责任、稳定复用或不同变更节奏。另一个场景应能复用主体和证据，而不被迫导入受益所有人判断规则。

### 8.3 变更看影响而不是操作类型

新增公理也可能改变已有推论；修改注释可能不改变语义。版本升格依据应是既有能力问题、映射和消费者合同是否受影响，而不是机械按增删分类。

活动路径中删除已废弃定义和实现，不增加长期兼容层。历史归档保留当时输入、模型、规则与执行配置，供回放；历史留档不等于继续支持旧接口。

### 8.4 完成与停止

当声明范围内的能力问题有证据、预期禁止结果得到检查、实例能够映射、依赖与发布边界清楚时，可完成该版本。未支持范围单列，不继续无限追问或无限建模。

本册不承诺仅凭本体自动获得业务真相。它规定的是：团队如何对业务含义作出可审查的承诺，并让后续数据和程序能够检验、共享和正确使用这些承诺。
