# 金融领域本体语义工程实施规范
## V2.0｜审阅修订版

**文档职责：**规定如何组织人员、生产制品、执行验证及交付可复用的领域语义资产。

**基线与日期：**以本次对话生成的第二册 V1.0 为基线；2026年9月7日。概念方法见第一册；已执行范围与参考数据见第三册。

## 1. 适用范围与基本纪律

本规范适用于新建、修订、映射、审计和交付金融领域语义资产。一次任务必须先明确是只读审阅、设计、生成、修复还是发布；没有写入授权时，不修改来源、仓库或业务系统。

交付合格不以文件数量衡量。必须能够沿一个能力问题追踪到定义、依据、实例、查询或计算、预期答案及实际运行证据。技术检查不能证明材料真实、法规适用正确、客户身份核实完成或公开发布已获授权。

发布状态分为：**探索草案、可执行候选、经授权发布**。前两者可以保留未执行项和明确限制；后一状态必须满足该项目事先约定的强制门禁。资料不齐时，不能用空文件、假值或伪造通过记录完成清单。

## 2. 角色、决策责任与有界协作

### 2.1 角色责任

| 角色 | 对结果负责 | 不可代替的责任 |
|---|---|---|
| 业务负责人 | 范围、价值、业务验收与采纳范围 | 不以业务意见替代技术运行证据 |
| 领域专家 | 定义、制度适用、关键事实口径和案例裁定 | 不把尚有争议的问题伪装成唯一正确答案 |
| 本体工程人员 | 概念、关系、形式语义、推论边界 | 不替业务方签署核实或审批 |
| 数据工程人员 | 来源模式、标识、映射、质量与时间转换 | 不编造真实表结构或缺失数据 |
| 验证人员 | 独立预期、执行记录、反例和回归 | 不直接用被测输出生成黄金答案 |
| 资产负责人 | 依赖、版本、发布范围和许可检查 | 不将工具检查通过等同于公开授权 |

小团队可以一人兼任多个角色，但记录中应区分设计者、预期制定者和批准者。尚未进行独立复核时，报告写明“作者自检”，不能写成独立专家验证。

### 2.2 证据优先与澄清预算

先读现有对话、附件、制度、源数据模式和已有资产。能通过可访问资料核实的事实不得转交用户代查；低风险、可逆的设计可采用推荐方案并留痕。

默认最多集中澄清一轮、最多五个高影响问题。每题应给出推荐、理由、受影响资产及不答时的处理。只有用户明确要求研讨、访谈或逐项挑战时，才进入多轮讨论。

预算限制打断次数，不减少事实真实性要求。缺失真实字段、法定阈值、权限、审批或身份事实，不能归为可逆假设；预算耗尽后仍应局部阻塞。用户沉默不构成批准。

### 2.3 不确定性与依赖

| 分类 | 处理 | 对外呈现 |
|---|---|---|
| 已有依据 | 使用并关联来源 | 已知内容 |
| 可推导 | 记录输入和推导方式 | 推导结论，不冒充直接来源 |
| 可逆设计假设 | 采用默认，检查影响 | 假设及可修改范围 |
| 高影响待决策 | 进入有界澄清 | 推荐及待确认事项 |
| 必要输入缺失 | 阻塞依赖它的资产 | 缺少什么、影响什么、其他已完成什么 |

例如，缺真实数据库模式时，可以完成术语、概念模型和合成实例验证；真实映射及依赖真实映射的发布仍受阻塞。不能一概规定“任何缺映射都阻塞纯本体发布”，必须按本次目标依赖判定。

### 3.3 工作表使用规范

每项在原文旁另填：本场景业务陈述、依据及定位、适用状态、关联概念或动作、验证方法。每项可有多条具体陈述，不能只照抄原问题；不适用项必须说明边界。

填写顺序是资料萃取、交叉核对、低风险设计、必要专家补充。禁止把29项直接变成必须逐题问用户的访谈，也不要求创建29类本体结构。书中“描述清晰、逻辑正确、内容完备、极简表达”在本规范中以本次能力问题的范围判定，不以穷尽领域为目标。[S1]

## 4. 标准生产过程

### 4.1 以可验证切片而非横向文件批次推进

每个切片执行：范围与问题 → 来源与术语 → 概念及消费合同 → 最小机器表达 → 映射或合成实例 → 正反例 → 证据与限制。完成后继续下个切片，已有测试保持可重复。

不先写完全领域模型再测试；不先建所有类、再等所有表、最后一次性运行。需要高风险人工确认的分叉单列，其不相关部分可先完成。

### 4.2 阶段产物和退出条件

| 阶段 | 最少信息 | 退出条件 |
|---|---|---|
| 范围与问题 | 目标、排除项、消费者、验收契约 | 能判定输出对错及何时允许未知 |
| 来源与萃取 | 来源目录、术语、29项适用性 | 关键定义有依据，分歧公开 |
| 概念与合同 | 粒度、身份、时间、计量、事实视图 | 核心正反例能无歧义表达 |
| 机器实现 | 模型、约束、映射、查询与配置 | 文件可解析，依赖完整 |
| 验证 | 精确预期、禁止结果、实际执行 | 检查有覆盖，失败可定位 |
| 发布 | 版本、摘要、依赖、许可和责任 | 强制项通过，限制及未执行项明确 |

### 4.3 信息组织而非文档数量

沿用项目已有标识、模型IRI和文件路径。来源、能力问题、建模决定、模型元素、映射及测试之间建立引用，避免再造相互重复的编号系统。

单个Markdown（轻量标记格式）文件可承载多张卡；机器字段的权威定义应只有一份，说明文档引用它。不能同时手工维护三个不同版本的同一约束。

## 5. 必须能够复用的模板

### 5.1 范围与能力问题契约

| 字段 | 内容要求 |
|---|---|
| 问题标识与自然语言 | 标识稳定，问题可单独理解 |
| 输入及上下文 | 目标、业务时点、知识截止、制度或政策版本 |
| 数据与覆盖 | 查询哪份图或事实视图，完整性由谁声明 |
| 执行责任 | 显式查询、推理、算法、规则或人工 |
| 正向预期 | 精确集合、数值、图结构或状态 |
| 反向预期 | 明确不得返回、不得推导的对象或结论 |
| 不足处理 | 缺失、冲突、未知、不支持和执行错误的输出 |
| 运行入口 | 测试命令、文件及工具配置 |
| 依据与裁定 | 来源、预期制定者、独立复核状态 |

### 5.2 概念卡与关系卡

概念卡：首选名称、定义、相邻非同义概念、粒度、身份、上位类型、生命周期、时间和计量、正例、反例、来源、能力问题。

关系卡：含义、方向、参与者类型、是否多元、业务基数与显式字段要求的区别、时间、是否独立引用、是否具有可组合性、禁止推论。不能把“相关”作为未解决问题的占位且宣布已完成。

### 5.3 身份映射卡

至少记录来源记录标识、现实主体标识、发放主体与范围、匹配依据、确认状态、别名与更名、有效期、重复导入策略和错误合并处理。候选匹配与确认同一性分别保存。示例采用合成标识时须注明，不声称已接通真实企业库。

### 5.4 断言与采信卡

断言卡：陈述主体、属性或关系、值及口径、适用时段、来源记录、上游来源链、观测和记录时间、材料定位、已知缺口。

采信卡：本次任务、选入和排除的断言、依据或政策、记录者、采信时间、替代关系、待解决事项。合成采信记录必须写明“演示记录”，不得使用真实审批式措辞暗示业务批准。

### 5.5 数据映射卡

| 映射方面 | 必须写明 |
|---|---|
| 源模式 | 实际文件或接口模式及版本；没有时标记缺失 |
| 目标 | 模型概念、属性或关系的真实标识 |
| 转换 | 类型、比例尺度、单位、枚举和日期转换 |
| 身份 | 来源主键如何关联主体和权益，不按姓名盲合并 |
| 异常 | 空值、不适用、冲突、非法值分别处理 |
| 输出 | 原始断言与采信事实视图分别写往何处 |
| 验收 | 来源语义→实例→查询还原的往返案例 |

### 5.6 语义决策记录

仅在变更代价高、未来读者难以理解且确有替代方案时记录。内容包括问题、上下文、方案、决定、依据、后果及受影响问题。普通命名修订不需要完整决策档案。

## 6. 实例与阶段质量门禁

### 6.1 四个不同阶段

| 阶段 | 可以保存什么 | 不允许做什么 |
|---|---|---|
| 来源保存 | 不完整文档、缺字段记录、错误线索 | 因不完整直接销毁来源；补造值 |
| 结构表达 | 有来源和明确缺口的断言 | 将来源声称无条件当成已采信事实 |
| 计算输入 | 身份、时点、计量与冲突满足计算合同的事实 | 缺比例填0；时间未知当永久有效 |
| 业务认定 | 适用规则和核实要求得到满足的结果 | 用查询空集自动证明不存在或批准兜底 |

### 6.2 约束应绑定阶段

一个原始记录缺比例可以合法保存，但在要求比例的计算阶段应失败。各约束须说明检查哪个图、哪个阶段和哪个对象范围；未知、违规和执行错误采用不同诊断。

业务完整性声明与算术合计不能互相替代。所有股权合计为100%是支持条件之一，不自动证明来源完整、无代持或控制安排已经核验。

## 7. 执行配置与验证

### 7.1 执行清单

每次可复现验证应锁定：输入快照、模型文件、约束文件、映射、查询或算法、规则与采信政策、语言配置、工具和依赖版本、导入闭包、图范围、时区、推理方式和执行顺序。无网络环境下不能悄悄使用未取得的远端导入。

本体语言不同配置的支持范围不同；工具可解析不代表支持其中全部公理。[S2] 不强制所有项目使用完整描述逻辑推理，但声明“逻辑一致性通过”时必须提供相应执行证据。

### 7.2 检查结果的统一语义

| 结果 | 含义 |
|---|---|
| PASS（通过） | 实际执行，且符合本项预期 |
| FAIL（失败） | 实际执行，但不符合预期 |
| ERROR（执行错误） | 工具或数据导致无法完成该检查 |
| NOT_EXECUTED（未执行） | 没有运行，或缺依赖 |
| UNSUPPORTED（不支持） | 超出所选执行能力 |
| NOT_APPLICABLE（不适用） | 经范围判断无需该检查，并有理由 |

有效负例应由“得到预期违规”使测试通过，不能把任意异常当成验证成功。报告的测试通过率与被测数据的符合性分开：一个负例测试通过，通常意味着被测负例正确地不符合约束。

### 7.3 发布检查矩阵

| 检查 | 关键证据 | 不能替代的内容 |
|---|---|---|
| 语法与引用 | 全文件解析、引用可解析、依赖存在 | 业务含义正确 |
| 配置符合 | 声明语言构造在执行范围内 | 完整逻辑一致性 |
| 逻辑与推论 | 一致性、可满足性、希望与禁止推论 | 数据字段已显式填齐 |
| 数据符合性 | 指定目标、阶段、违规明细 | 来源真实性 |
| 能力问题 | 输入固定、正反预期精确 | 未来未见业务全部正确 |
| 映射往返 | 原始记录与语义还原一致 | 实体消歧已被证明完美 |
| 变更回归 | 受影响与不应受影响用例 | 自动批准所有消费者升级 |
| 发布完整性 | 文件摘要、版本、许可、敏感项检查 | 业务及法律专项认证 |

### 7.4 防止空验证

SHACL（形状约束语言）根据目标选择节点，再检查相应约束。因此仅看符合性布尔值不足以证明覆盖。[S3]

每个检查应记录预期对象集合或数量、实际目标集合或数量、执行约束、跳过项、工具错误和违规。若预期一个对象却选中零个，即使没有违规也应判该验收失败。若用例本来预期零对象，零目标可以合法；不能机械地把所有零目标判错。

约束文件自身也应校验。约束解析或元校验未执行时，报告不得写“约束模型已验证”。第三册提供一个独立目标覆盖测试和可选的标准约束引擎入口。

### 7.5 最小正反例及变形检查

必备检查包括：同一权益重复证据不翻倍；同名不同主体不合并；已失效关系不进入当前视图；缺值不被补零；错误约束目标被覆盖检查发现；改变比例尺度被拒绝；展示舍入不影响边界；不支持环路时明确停止受影响计算。

还应检查语义等价的变换不改变结果，例如调换三元组顺序。原始字节摘要用于源完整性，图同构用于图结构比较，两者证据目标不同。[S4]

黄金案例的期望应在运行前独立写定。未做专家复核时说明作者制定，不假称“银行已确认”。分歧保留为待裁定项。先验证小型反例再验证综合场景，避免大案例只证明演示能够运行。

## 8. 发布、演化与安全

### 8.1 最小交付组织

发布至少能找到范围与问题、来源与术语、建模决定、机器模型、约束、映射或其缺失状态、实例、查询与预期、执行入口和配置、结果报告、版本及许可说明。可按已有项目目录组织，不强制十四份独立文档。

推荐让一个清单引用真实路径，测试验证路径存在、标识唯一和引用闭合。文档可以合并，机器资产不复制多份作为不同“权威版本”。

### 8.2 发布前检查

首先确认写入与目标权限；再验证制品和测试；最后检查材料敏感性与再分发依据。存在未完成强制门禁时只能交付候选，不以“能打包”冒充“可生产”。不发布客户原始证据、身份证件、密钥和真实连接配置到公开仓库。

第三方原文可为内部学习引用，不因此获得完整公开再分发许可。合成样例须显式标识；脱敏也不自动等于所有再识别风险已消失。对未知许可或外部上传权限，停止相关发布，但保留本地工作成果。

### 8.3 变更与回放

版本决策应比较含义、身份规则、允许推论、约束、映射和消费者合同的变化。新增定义也可能破坏既有行为；不要机械将“新增”视为无风险。

每次发布归档输入及依赖摘要、模型与规则、查询和计算代码、采信记录、执行配置和结果证据。历史留档不意味着维护旧接口兼容层；当前路径去除已废弃实现，必要的新版本重新验证消费者。

### 8.4 复用与效率验收

新场景启动时，先选现有概念、实例和测试，只新增真实差异。衡量首个有效切片耗时、关键语义缺陷、映射缺陷和已有资产复用情况，不以类数量作为成功指标。

发布前至少由一位未参与主要编写的人按清单尝试运行；没有进行此项时如实标记。可执行技术候选不自动成为业务批准版本。

## 9. 交付验收记录模板

| 项目 | 待填写内容 |
|---|---|
| 本次目标与范围 | 完成哪个问题；排除哪些结构 |
| 版本和输入 | 制品版本、输入摘要、知识截止 |
| 已完成制品 | 真实路径及用途 |
| 实测结果 | 命令、退出码、用例及证据路径 |
| 未执行或不支持 | 原因、影响及补验入口 |
| 假设和待决策 | 只列影响使用的内容 |
| 阻塞资产 | 输入缺失及其依赖范围 |
| 业务与授权状态 | 谁审核、谁批准；未做则写未做 |
| 发布范围与资料权限 | 内部或公开；来源许可依据 |

验收结论应写成“在某范围、某配置下完成了哪些检查”，而不是无条件的“本体正确、生产可用”。
