# 本体语义构建方法

## 1. 第一性原理

本体不是数据库的另一个格式，也不是“把名词画成节点、关系画成边”。本体要显式回答：

1. 业务世界中存在什么；
2. 它们分别是什么；
3. 它们之间是什么关系；
4. 哪些语义约束必须成立；
5. 在什么时间、来源和上下文下成立。

本体语义构建的目标，是把专家对业务世界的稳定认知转化为机器可理解、可验证、可复用的领域世界模型。

## 2. 本体与其他逻辑的边界

- Ontology（本体）：世界是什么。
- Axiom（公理）：世界中稳定成立的语义规律。
- Constraint（约束）：实例数据要合法必须满足什么。
- Computation（计算）：数据怎么算。
- Business Rule（业务规则）：什么条件产生什么判断。
- Process（流程）：任务如何执行。
- Action（动作）：判断后可以或必须做什么。

ECP（企业认知平台）会把这些能力拆到不同资产中；不要把所有业务逻辑硬塞进 TTL。

## 3. 八步法

### 第一步：范围

定义领域边界、包含项、不包含项、依赖领域和目标消费者。范围应该由业务问题决定，而不是“描述整个行业”。

### 第二步：能力问题

用 5–20 个 Competency Questions（能力问题）定义“模型建成后必须回答什么”。能力问题既限定范围，也是验收合同。

示例：

- 给定企业和业务日期，当前有效的直接股权权益有哪些？
- 某一关系的事实来源和证据是什么？
- 两个来源对同一事实是否存在冲突？

### 第三步：知识萃取

从法规、制度、操作手册、数据字典、接口、历史案例和专家访谈中收集显性与隐性知识。

可以使用“29句话”作为知识萃取模板，使用“7+1”作为语义覆盖检查，但二者不是 ECP 的技术实现规范。

重点讲清：

- 有哪些对象；
- 对象如何关联；
- 对象如何分类；
- 术语如何定义；
- 哪些事实和规则影响判断；
- 哪些步骤、权限、数据操作与目标相关。

### 第四步：概念化

这是最关键的一步。对每个候选概念判断它属于：

- Entity（实体）
- Relation（关系）
- Relational Entity（关系实体）
- Role（角色）
- Event（事件）
- State（状态）
- Value Object（值对象）
- Assertion（事实断言）
- Evidence（证据）

如果一个“关系”自身具有属性、时间、来源、证据、状态或生命周期，应优先考虑实体化。

例如“张三持有 A 公司 60% 股权”不应机械建成一条带 60% 标签的边；如果还要表达股份类型、生效日期、终止日期、表决权和证据，应把“股权权益”建成独立对象。

### 第五步：语义精化

对核心概念明确：

- 稳定 IRI 身份；
- 中文首选名称；
- 业务定义；
- 上位/下位概念；
- 关系方向与 domain/range；
- 时间语义；
- 数据来源与证据语义；
- 两条记录何时代表同一现实对象。

避免“相关、关联、涉及”等含义不清的通用关系。

### 第六步：ECP 形式化

只在概念模型稳定后，才映射到 ECP Semantic Profile 1.0 支持的 RDF/RDFS/OWL 有限子集。

不要从数据库表直接生成 Class；不要为了表达业务规则而使用 ECP 不支持的 OWL、SWRL 或 SPARQL 构造。

### 第七步：实例化与 Mapping（映射）

将真实数据映射到语义对象。每项映射需要说明：

- 来源数据源；
- 表/视图与字段；
- Record Key（记录键）；
- Entity Identity（实体身份）；
- Property/Relationship（属性/关系）映射；
- 空值、基数和 Coverage（覆盖度）策略。

没有真实 Schema（模式）时，不生成可导入 Mapping。

### 第八步：验证

依次验证：

1. Turtle/JSON 语法；
2. ECP Profile 支持边界；
3. SHACL/Mapping/规则跨资产一致性；
4. 实例能否表达真实业务案例；
5. Competency Questions（能力问题）是否可以回答；
6. ECP 平台预检和候选编译是否通过。

## 4. “7+1”在本技能中的位置

“7+1”只作为业务语义覆盖检查，不直接决定 ECP 技术资产：

| 业务语义维度 | ECP 中的主要承载方式 |
|---|---|
| 业务资源描述 | ONTOLOGY + MAPPING |
| 分层约束 | ONTOLOGY 有限公理 + SHACL |
| 业务术语 | `rdfs:label` / `rdfs:comment` / `skos:prefLabel` 元数据 |
| 业务控制规则 | DERIVATION / EVALUATION；不是 SWRL |
| 流程活动与操作 | ECP 语义资产只建必要概念；一般流程编排不属于 Ontology；语义变化动作可用 ACTION_POLICY |
| 权限管控 | 主要属于平台治理/部署边界；不要伪造 ODRL 执行语义 |
| 数据操作 | MAPPING、SCOPE 和 Fact Provider 边界；ECP Profile 不提供通用 SPARQL Runtime |
| 目标与评估 | Competency Questions + EVALUATION + 测试合同 |

## 5. 完成定义

一个本体语义模型只有同时满足以下条件才算完成当前阶段：

- 范围明确；
- 能力问题明确；
- 核心知识有来源；
- 概念化完成；
- 关键术语无歧义；
- 能用 ECP 支持的语义构造表达；
- 真实数据能够映射；
- 本地验证通过；
- 能力问题可以由生成资产支撑；
- 平台级可发布性仍由 ECP 预检和编译证明。
