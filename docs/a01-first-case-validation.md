# A01 首例贯通验证：先得到结果，再根据问题改进

本文是待执行方案，不是运行报告。保留已合并的五技能及文档输入边界，不增加合同、必交文件、共享依赖或技能版本。

## 1. 本次只证明一件事

在隔离测试环境，用一个预期明确的 A01 用例，让现有知识、模型、平台编制、数据映射和发布流程衔接起来，实际执行并核对结果。通过后只声明这个用例和分支已验证，不代表全部受益所有人业务完成。

优先选已有的普通公司直接或间接权益计算案例，复用以下材料，不重做全量知识和模型：

- `A01受益所有人/01业务输入`：原始业务材料。
- `A01受益所有人/02数据源与表结构`：现有数据结构。
- `A01受益所有人/03领域知识输出`、`04领域模型输出`：固定本次使用的已有版本及案例。

案例输入与预期先独立核对，不能由待验证的实现自己生成答案。脱敏或合成数据必须注明性质；例如单一路径中，甲持有乙公司 60%、乙公司持有丙公司 50%，计算预期为 30%。是否符合认定标准，仍由选定知识版本决定，本文不新定业务口径。只缩小本次测试范围，不删减上游模型来制造“全量完成”。

## 2. 前置文档处理怎么落地

直接核验公司现成文档解析服务的实际接口、权限和返回内容；不新建服务仓库、文档网关或通用适配框架。调用及少量字段整理放在现有调用端或测试工作目录，不放回知识技能承担原始文件解析。

先用一份已授权材料调用服务，保存真实响应，并按现有 `source_units`（来源单元）输入要求整理文本、表格内容、原文定位和摘要。只做已确认接口所必需的字段适配，不猜接口、不添加新格式。相关合同仍在 `domain-knowledge`（领域知识形成）技能内，不搬目录。

已有可用解析结果可以直接复用来验证后半段，但须注明本轮未重测解析服务；未经真实调用，不能把前置服务记为已验证。没有可用接口或权限，就记录缺少的具体条件，先验证不依赖它的部分，不用模拟响应冒充真实接入。

## 3. 沿现有链路逐段执行

| 顺序 | 做什么 | 本段应看到的实际结果 |
| --- | --- | --- |
| 1. 知识与模型 | 核对选定规则、对象、关系、案例和版本；让业务同事按这个案例审阅 | 能说明输入事实、判断步骤和预期结果；不清楚的地方只修对应内容，不增加呈现架构 |
| 2. 平台编制 | 用当前模型交接给编制技能，先验证能否接收，再生成本例所需平台资产 | 实际交接和校验输出；不能接收时，针对失败定位修复接口，不绕过合同 |
| 3. 数据映射 | 按已有真实表结构准备测试记录，生成或复用现有映射 | 平台实际读取并生成预期事实；核对身份、关联、比例尺度及判断时点，不只检查映射文件存在 |
| 4. 发布与运行 | 沿既有入口在授权测试环境完成编译、发布并实际运行 | 保存实际回执、运行标识和原始结果；打包、导入或编译成功不能代替运行完成 |
| 5. 结果核对 | 将实际结果与独立预期比较；同一固定输入复跑一次 | 业务结果一致；使用现有输出或日志能够定位本例使用的测试记录和关键计算 |

先做正常路径，再改变一个输入验证结果会按业务规则变化，并做一次关键数据缺失验证。缺失时应遵守已有模型的未知或阻断规则，不能用零值、否定或人工兜底掩盖失败。这些是本例检查，不要求另建测试平台。

已有业务确认、访问权限和发布授权要求继续有效。缺少确认或授权时，可以验证允许范围内的静态或离线环节，但不能越过门槛，也不能声称已贯通。

## 4. 数据从哪里来，先用现有信息回答

先使用已有映射中的源表字段、记录键、关联与转换说明，以及平台实际提供的日志和结果解释；不新增 `data-lineage.json`（数据血缘文件）、血缘合同或强制交付门槛。

测试时保留本次使用的输入记录及版本，用实际输出核对计算来源。若确实定位不了某个错误，就在实际发生问题的位置补最少的记录信息或日志，并复跑验证；不预先设计整套血缘体系。没有平台证据时，不宣称已经具备运行期行级追溯。

## 5. 用什么作为完成证据

将本轮输入版本、实际命令或接口、预期与实际结果、原始日志位置、失败原因和复跑结果，记入 `A01受益所有人/过程与评审记录` 下本例的一份运行记录。沿用现有产物及引用方式，不增加报告格式或机器合同。

只有实际运行完成、正常结果符合预期、变更输入得到相应结果、缺证没有被误判、固定输入复跑结果一致，才记为“本例贯通验证通过”。其余如实写“检查通过”“未执行”或“受阻”，说明停在哪一步；合成本例不能代替真实客户业务验收。

遇到问题，按“复现错误 → 最小修复 → 同例复测”推进。首例之前不为预想的血缘、扩展或部署需求做通用重构；已经证实阻塞正确运行的问题应及时修复，不要求先积累多个案例才允许改。
