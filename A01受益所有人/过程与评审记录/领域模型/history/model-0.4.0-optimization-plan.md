# 下一步优化方案：业务语言、模型内容和可验证性

固定输入：03领域知识输出2.1.0；范围41问题、59规则、86案例、15OPEN。技能工程采用qiaomu-meta-skill，当前0.7.0为开发候选。该方案不以YAML行数或对象数量验收。

## 1. 先检查抽象是否成立，再选择名称

逐对象回答：现实中是什么、谁能举出一个实例、如何识别同一实例、与什么对象有关、何时发生变化、由什么证据支持。实体、业务角色、关系、判断结果、计算中间量分别选择表达方式，避免把一句计算描述名词化后升成对象。

例如：自然人和非自然人主体保存稳定身份；受益所有权关系连接某人、某主体及生效终止；股权/收益/表决权/实际控制是认定依据或关系属性。当前形成日期由经核实的连续历史得出；真实中断作为历史保留。“分类型受益所有权资格”不继续作为默认对象名。改名不自动证明对象划分正确。

产物：模型内的名称来源、业务句子、正反例、身份和独立建模理由。验收：只看名称与实例，业务人员能说明这是什么记录、何时新增、何时仍为同一记录。

## 2. 用业务链路检查模型连接

先完整走通识别、国企适用性与风险判断、形成日期回访、差异闭环，再覆盖备案、查询、报告、异步反馈等全量过程。每一步要能从对象和输入事实追到判断、输出、证据与历史。

已授权业务口径保留：国企性质→适用性→风险→简化；形成日期使用最近一段连续达标的起点并保留中断；实际更正并复核一致闭环；30日作为更新期，不作日期容差。

验收：不允许有只有名称、没有主体或承担者的关系；不允许有说明文档写了而DSL未表达的判断。

## 3. 逐条规则做七项对照

每条规则核对范围、前提、条件、结果、例外、缺证、时间。每项必须关联实际字段、表达式、约束、状态迁移或人工准则。形式引用通过后仍需对照知识原文逐项语义审查。

计算规则、固有人工判断、未决业务口径分别处理。固有人工判断明确证据、责任人、准则、记录和复核；语言缺少计算能力不伪装成人工判断；上游OPEN不自行关闭。

验收：59条规则都有实质对应；41问题与86案例完整保留；没有因只选示例而被遗漏的问题。

## 4. 验证结果和停止条件

先验证关键计算及迁移边界，再逐项审查全部案例。包含25%及其下方、多路径、未知数据、循环结构、连续与中断历史、风险门控、年月差异、待更新、承诺更正与实际更正、请求已受理与实际成功。

每项保存输入、预期、实际、模型与脚本摘要。结构通过、解释完整、实际求值、独立语义审查和业务批准分别记录。计算类用现有CLI，人工裁定类审查准则与证据要求，未决事项类检验是否正确停止；不能一律打执行PASS。

当前新增记录约束检查与精确小数计算尚待行为验证。

## 5. 同一模型生成两种读物

review.md面向业务：业务名称、场景、判断步骤、案例与待决定问题。coverage.md面向审计：内部标识、字段、规则要素及证据对应。二者都从model.yaml生成；模型变更后重新生成，不分别手工维护。

交互评审按问题或案例反馈；线下评审带版本、范围和责任人回流。技能结束不自动等于评审结束，局部确认不自动成为整版确认。

## 6. 收敛交付与通用性

保留唯一当前model.yaml入口，旧版归档。再用一个订单领域实例验证身份、输入输出绑定、未知传播和业务阅读要求，避免将A01专用规则写进通用技能。归档准确的qiaomu评估与缺失证据；不宣称未执行的服务评估、安装或业务批准已通过。

当前已落盘：完整范围DSL0.3.0及同源稿；结构和生成合同PASS。接下来优先级：独立语义审查→关键案例验证与修正→全量案例审查→质量评估和交付收敛。业务确认保持PENDING。
