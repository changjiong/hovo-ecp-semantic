domain-knowledge：输入、处理、输出

这张图解释技能的合同和处理边界。它把“必须做什么”“脚本实际检查什么”“业务人员仍需确认什么”分开。

一条主链

01 输入登记

材料与目标

读取业务目标、消费者、范围和来源。每个来源变成 SourceRef，带路径、摘要、来源主体、日期、定位和权威级别。

→
02 业务抽取

形成认知

从材料中整理陈述、术语、业务问题，说明事实、依据、判断步骤、结果边界和缺证处理。

→
03 业务组织

规则与案例

把判断写成规则，把正例、反例、边界和缺证写成案例，并登记分歧、缺口、影响和待确认事项。

→
04 评审与交付

可读说明书

输出业务主文档 review.md，结构化附件 output.json，再执行合同、引用、摘要和文档锚点检查。

输入到底是什么

结构化输入 input.json

PRODUCE需要 business_goal、consumers、sources。

REVIEW需要已有成果引用 subjects。

REVISE需要 subjects、change_request、变更依据 sources。

Schema 只检查字段类型、必填项和引用形状；它不读取 PDF 内容，也不判断业务语义。

中间每一步产出什么

步骤处理逻辑形成的业务对象停止条件 / 风险
条款覆盖建立文件、版本、生效信息、条款号、原文定位和主题的覆盖矩阵。来源索引、覆盖记录、未覆盖缺口。条款没有定位或只写“全文”时，不能声称全量覆盖。
陈述抽取把“材料写了什么”与“整理者推断什么”分开。statements：文本、来源、依据、origin、确认状态、争议。没有依据不能变成 SOURCE_STATED；推断要有支撑陈述。
概念整理解释定义、边界、同义词、相邻但不同的概念、实例和反例。terms：定义、别名、关联陈述、区别。不能把物理字段名直接当业务概念。
问题展开按业务标题说明谁使用、要知道什么、依据为何适用、如何判断、结果边界和缺证动作。questions：问题、消费者、决策用途、未知政策。不能用“调用规则引擎”代替业务判断。
规则组织明确范围、前提、条件、结果、例外、缺证行为、有效期、责任。rules：关联陈述和问题。规则冲突不能静默合并；不确定时保留 OPEN 或 PENDING。
案例覆盖按问题配正例、反例、边界、缺证案例，记录预期和禁止结果。cases、case_coverage。案例预期不能由新写的规则自证；合成案例不能冒充客户事实。
交互评审IN_SESSION 收集真实答复、角色、时间、范围；DEFERRED 保留待审并记录恢复入口。confirmation、states、issues。作者自查、脚本通过、智能体意见都不等于业务批准。

输出是什么

业务主交付物：review.md

必须能脱离 JSON 阅读，包含范围全貌、概念、判断说明、案例、访谈清单、来源索引、确认记录。

用 HTML 锚点把正文段落绑定到 K.Qxx、K.Txx、K.Rxx 等对象。锚点只证明“有定位”，不证明内容正确。

结构化附件：output.json

核心：content.sources、statements、terms、questions、rules、cases、case_coverage。

治理：顶层 issues、trace、states、confirmation 和 files。

脚本真正检查什么

validate_contract.py
├─ --check-schemas
│  └─ 加载 bundled Schema、解析 $ref、检查 Schema 本身有效
└─ validate input|output FILE --project-root ROOT
   ├─ JSON 唯一键、有限数值、普通文件、禁止路径与符号链接
   ├─ ArtifactRef 的 path 与 SHA-256 digest
   ├─ id / source_id / evidence_id 是否重复
   ├─ evidence_ids 是否能找到 evidence 定义
   ├─ domain_checks.check_content()
   │  ├─ 来源、陈述、术语、规则、问题、案例引用
   │  ├─ supporting_statement 无循环
   │  ├─ case_coverage 是否逐问题覆盖
   │  └─ 冲突、缺口、案例类型是否一致
   └─ output 专属
      └─ review.md 非空、版本一致、章节锚点齐全

最需要继续核对的地方

核心缺口：技能现在新增了“逐条制度覆盖”的要求，但合同 Schema 和校验器仍只检查 7 类对象与文档锚点，没有检查“每一条制度条款是否被覆盖”。因此，当前 PASS 不能推出“抽取完整”。

建议的下一步：增加显式的 article_coverage 合同对象，至少包含来源、条款编号、原文定位、业务主题、覆盖对象 ID、覆盖状态和未覆盖原因；校验器再检查每份制度原文的条款集合是否一一覆盖。
